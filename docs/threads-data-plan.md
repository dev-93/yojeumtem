## 1. 해결할 문제와 완료 모습

캡처나 PDF를 반복 전달하지 않고, Notion에서 **어떤 글을 언제 썼고, 그 글의 반응이 현재 어떤지** 확인한다. 여러 AI는 같은 Notion 링크와 연결된 게시글 DB를 읽어 맥락을 파악한다.

사용자가 실제 글을 쓰면 수집기가 본문·URL·성과를 Notion에 반영한다. 프로젝트 홈에는 데이터 기준 시각과 사실 중심의 두 줄 요약을 표시한다. 게시글 DB에서 원문과 수치를 확인할 수 있어야 하며, 요약만으로 전체 게시글을 읽었다고 간주하지 않는다.

계정의 목적은 사업 방향 탐색, 성장, 커뮤니티 형성이다. 기존 글은 말투·대화 맥락·중복을 확인하는 참고 자료이며, 조회수가 이후 주제나 고객군을 자동 결정하지 않는다. 이 문서는 기술 구현 계획이며 프로젝트의 사업 현황·실험 결과를 로컬에 중복 기록하지 않는다.

## 2. 1차 범위

| 포함 | 범위 |
|---|---|
| 계정 | 사용자가 인증한 본인 Threads 계정 1개 |
| 게시글 | API에서 조회 가능한 기존 게시글, 이후 신규 게시글 |
| 본문 | 원문·게시 시각·원문 URL·유형·인용/리포스트 여부 |
| 성과 | 조회·좋아요·답글·리포스트·인용·공유의 최신 누적값 |
| Notion | 게시글 DB 1개, 프로젝트 홈의 전용 요약 영역 |
| 동기화 | 수동 실행부터 검증하고 이후 하루 2회 배치 |
| 요약 | 기준 시각·수집 범위·최근 게시글/반응의 숫자를 두 줄로 표시 |

댓글 원문·외부 고유 응답자·재참여 분석·시간별 성과 이력은 2차로 둔다. 댓글 수만으로 대화의 질이나 커뮤니티 형성을 판정하지 않는다.

자동 게시, 자동 답글, 판매 상품 선정, 주제 강제 분류, 별도 웹 대시보드, 유료 LLM 요약 API는 1차에 포함하지 않는다. 기존 글감 추천 예약의 변경·신규 생성도 이번 구현 범위가 아니다.

## 3. 확인된 API 범위와 검증할 항목

공식 문서 확인 기준: 2026-11-17. 구현 착수 시 계정의 실제 API 응답과 대조한다.

| 항목 | 근거와 처리 |
|---|---|
| 내 글 목록 | `GET /{threads-user-id}/threads`. `threads_basic` 권한, 페이지네이션 처리. [S1] |
| 본문·시간·URL | `text`, `timestamp`, `permalink` 등을 요청한다. 긴 텍스트 첨부가 있으면 `text_attachment`도 확인한다. [S1] |
| 게시글 지표 | `GET /{threads-media-id}/insights`, `threads_basic`와 `threads_manage_insights` 권한. [S2] |
| 지표 이름 | `views`, `likes`, `replies`, `reposts`, `quotes`, `shares`. 조회·공유는 개발 중 지표로 안내되어 있어 숫자의 변동 가능성을 고려한다. [S2] |
| 답글 수 | 루트 게시글의 답글 수는 전체 답글을 포함하므로 고유 사람 수나 직접 답글 수로 해석하지 않는다. [S2] |
| 리포스트 | 타인의 글을 리포스트한 항목에는 인사이트가 빈 배열로 올 수 있다. 원본 글과 분리한다. [S2] |
| 게시글별 프로필 방문·팔로우 | 확인한 게시글 인사이트 목록에는 없다. 1차 자동 수집 대상으로 약속하지 않는다. 화면에서 확인한 값은 수동 참고값으로 출처·확인일과 함께 별도 보존할 수 있다. [S2] |
| 계정 조회한 사람·관심사 등 | 화면/PDF와 API의 항목·정의가 같다고 가정하지 않는다. 1차 대상에서 제외한다. |
| 계정 인증 | Meta 앱 설정, 본인 계정 연결, 적절한 권한의 사용자 접근 토큰이 필요하다. 앱 설정·테스터 등록·필요한 승인 여부는 실제 개발자 화면에서 확인한다. [S1, S2, S5] |
| 인증 유지 | 장기 토큰 교환·갱신이 지원된다. 정확한 만료·갱신 조건, 저장 방법을 인증 단계에서 확인하고 운영에 반영한다. [S5] |

확인하지 못한 값은 `null/미확인`이며 0이 아니다. 과거 게시글의 과거 시점 성과를 현재 누적값으로 복원하지 않는다.

## 4. Notion 데이터 설계

프로젝트 홈 아래 `Threads 게시글` DB를 신설한다. 제목은 원문의 첫 부분에서 만들고 본문은 페이지 내용에 원문 그대로 저장한다. 아래 이름은 제안이며 생성 시 확정한 속성 ID를 코드에서 사용한다.

| 속성 | 타입 | 용도 |
|---|---|---|
| 게시글 | Title | 사람이 목록에서 구분할 짧은 제목 |
| Threads ID | Text | 중복 방지 기준 |
| 계정 ID | Text | 인증된 수집 대상 확인 |
| 원문 URL | URL | 실제 게시글 확인. 응답에 없으면 비워 둔다. |
| 게시 시각 | Date | API 원본 시각, 표시 기준은 Asia/Seoul |
| 유형 | Select | 텍스트·이미지·영상·캐러셀 등 응답값 |
| 원문 구분 | Select | 본인 원글·인용·리포스트 |
| 조회 / 좋아요 / 답글 | Number 각 1개 | API 누적값, 미제공은 빈 값 |
| 리포스트 / 인용 / 공유 | Number 각 1개 | API 누적값, 미제공은 빈 값 |
| 성과 관측 시각 | Date | 해당 수치가 실제 조회된 시각 |
| 본문 확인 시각 | Date | 게시글 내용을 마지막으로 확인한 시각 |
| 수집 상태 | Select | 정상·일부 지표 미확인·인증 오류·접근 확인 필요 |
| 직접 메모 | Text | 사용자가 쓰는 목적·느낀 점. 수집기가 수정하지 않음 |

페이지 내용은 `원문` 등 수집기가 관리하는 영역과 `직접 메모` 영역을 분리한다. 긴 본문은 Notion 제한에 맞춰 나눠 저장하고 원문을 요약으로 대체하지 않는다. 링크·텍스트 첨부·미디어 종류를 보존하되 영상 다운로드나 이미지 내용 해석은 1차에 하지 않는다. 이미지 중심 글은 텍스트만으로 내용을 모두 파악할 수 없음을 표시한다.

기본 보기는 `최근 게시글`, `조회순`, `답글순`, `수집 확인 필요`다. 성과 순위에는 게시 후 경과 시간을 함께 보여줘 노출 기간 차이를 확인할 수 있게 한다.

프로젝트 홈에 전용 영역만 추가한다. 기존 사업 목표·실험·기록을 통째로 덮어쓰지 않는다. API용 `data_source_id`와 사용자가 여는 DB 페이지 ID는 따로 관리한다. [S3]

## 5. 수집·갱신 정책

### 초기 수집

1. 인증 계정 ID와 사용자명을 확인하고 잘못된 계정이면 중단한다.
2. 페이지네이션으로 조회 가능한 과거 게시글을 순회한다. 초기 상한은 1,000개로 두고 도달하면 미수집 범위와 다음 커서를 표시해 이어받는다.
3. 전체 본문을 보관하고 조회 가능한 성과도 가져온다. 호출이 오래 걸리면 나눠 실행하되 완료 범위를 표시한다.
4. 최초 수집 시각의 누적값으로 기록한다. 예전 게시글의 24시간·48시간 성과로 표시하지 않는다.

### 정기 수집

- 제안 시각은 한국시간 09:00·18:00, 하루 2회다. 아직 예약하거나 배포하지 않은 제안이다.
- 신규 글 조회는 마지막으로 완전히 저장한 시각보다 48시간 앞선 구간부터 다시 확인하고 ID로 중복 제거한다.
- 최근 14일 글의 본문·성과는 매 실행 갱신한다.
- 14일 이전 글은 주 1회 갱신하고, 특정 오래된 글은 수동 재수집할 수 있게 한다.
- 늦은 반영·누락을 점검하기 위해 주 1회 목록을 다시 대조한다. 상한에 도달하면 부분 대조라고 표시한다.
- 목록에 한 번 없었다는 이유로 Notion 기록을 삭제하지 않는다. 개별 조회와 권한 오류를 확인한 뒤 접근 확인 필요로 표시한다.
- 성과가 내려가도 과거 최댓값을 강제로 유지하지 않는다. 실제 응답을 보존하고 변동을 표시한다.

기본 요청량은 게시글 목록 호출 수 + 갱신 대상 게시글 수에 비례한다. 기본 지표 6개는 가능한 경우 게시글당 한 번의 인사이트 요청으로 묶는다. 초기 실제 게시글 수와 응답으로 호출량을 계산한 뒤 운영 한도를 확정한다.

## 6. 동기화 안정성

- `(계정 ID, Threads ID)`로 기존 Notion 행을 조회하고 생성 또는 갱신한다. Notion 자체의 고유 제약에 의존하지 않는다.
- 동시에 두 실행이 쓰지 못하도록 단일 실행·잠금을 적용한다. 배치 전체가 실패해도 저장된 행을 다시 만들지 않는다.
- 마지막 완료 커서는 게시글 저장이 확인된 뒤 이동한다. 커서·재시도 이력은 기술 상태이며 사업 성과 문서와 분리한다.
- 지표 요청만 실패하면 기존 성과와 그 관측 시각을 유지한다. 본문 갱신 성공으로 성과도 최신인 것처럼 표시하지 않는다.
- 지표마다 부분 성공이 가능한 응답은 실패 항목을 명시한다. 시각이 다른 수치를 한 세트의 최신 수치처럼 섞지 않는다.
- 생성/추가 쓰기가 타임아웃이면 먼저 저장 여부를 조회하고 재시도한다. ID 기준 중복 검사 후에만 추가한다.
- API 제한은 응답의 `Retry-After`를 우선하고 지수 백오프·재시도 상한을 적용한다. 401/권한 오류는 무한 재시도하지 않는다. [S4]
- 토큰·앱 시크릿·인증 URL의 비밀 파라미터는 로그와 Notion에 남기지 않는다. 기존 `.env`와 `.runtime/`를 새 서비스의 유효한 설정으로 가정하지 않는다.

## 7. 두 줄 요약과 AI 전달 방식

1차 요약은 별도의 LLM 호출 없이 실제 수집 데이터로 생성한다. 인과 해석이나 다음 글 추천은 추가하지 않는다.

> 최근 7일 게시글 N개. 최근 글 중 조회가 가장 많은 글은 「제목」 V회, 답글이 가장 많은 글은 「제목」 R개다.
> 기준: YYYY-MM-DD HH:mm KST / 수집 N개 / 성과 확인 M개 / 미확인 K개. 글마다 게시 후 경과 시간은 다르다.

표시할 데이터가 없으면 채우기 위해 수치를 만들지 않는다. 문구는 예시이며 데이터량에 따라 더 짧게 줄인다. 과거 글의 누적 조회를 합쳐 최근 7일 계정 조회수라고 표시하지 않는다.

다른 AI에 전달할 기본 요청:

> 이 요즘템 페이지의 운영 목적·최신 요약과 연결된 Threads 게시글 DB의 최근 글 본문·성과·직접 메모를 읽어줘. 데이터 기준일과 읽은 범위를 밝히고 글감 하나와 추천 이유만 제안해줘. 과거 성과로 내 주제를 확정하지 말고, 겪지 않은 경험을 만들지 마.

각 AI의 Notion 연결·DB 조회 권한이 필요하다. 링크 전달만으로 모든 AI가 하위 DB 전체를 읽었다고 가정하지 않는다. 읽을 수 없는 경우에만 DB에서 텍스트/CSV로 전달하는 보조 경로를 둔다.

## 8. 구현 방식과 실행 환경

권장안은 TypeScript 배치 프로그램이다. 프론트 화면 없이 하나의 실행 명령으로 수집·검증·Notion 반영을 수행한다. 사용자의 익숙한 스택을 활용하고 새 서버 UI와 LLM 구독을 추가하지 않는다.

구현 시 추가할 모듈은 `Threads API 클라이언트`, `데이터 정규화`, `Notion 저장`, `동기화 조정`, `인증 갱신`으로 나눈다. HTTP 재시도와 비밀값 마스킹은 공통 계층에서 처리한다. API 버전과 의존성은 구현 시 공식 지원 범위를 확인해 고정한다.

로컬 검증 후 클라우드 배치로 옮기는 안을 우선한다. Mac이 꺼져 있어도 수집할 수 있어야 한다. 배포 제공자는 실제 비용·예약 지원·비밀값 저장·인증 갱신 토큰의 영속 저장 가능성을 확인한 뒤 결정한다. 갱신한 토큰을 다음 실행이 읽을 수 없는 일회성 환경은 그대로 채택하지 않는다.

ChatGPT의 글감 추천 예약은 이 수집 배치와 별개다. 추천 시 Notion의 마지막 수집 시각을 확인하며, 예약이 있다고 Threads 데이터 수집이 완료된 것은 아니다.

| 2. 수동 수집 | 페이지네이션·정규화·초기 수집·증분 수집 구현 | 게시글 목록을 빠짐없이 순회하고 재실행 시 ID 중복 없음 |
| 3. Notion 저장 | DB 스키마 생성·원문 보존·성과 반영 | 같은 명령을 두 번 실행해도 행 중복·메모 손실 없음 |
| 4. 요약·사용 검증 | 홈 전용 요약 영역과 DB 보기 연결 | Notion 링크에서 최근 글 본문과 기준 시각을 실제 확인 |
| 5. 배치 운영 | 비밀값·토큰 갱신·중복 실행 방지·배포 | 정기 실행 2회 이상 성공, 신규 글 반영과 장애 복구 확인 |

개발 착수에 필요한 사용자 작업은 Meta 개발자 계정에서 본인 계정을 인증하는 일과 Notion 통합에 대상 페이지 접근을 주는 일이다. Notion 연결 도구와 배치 프로그램의 API 인증은 별개이므로 실제 접근을 검증한다. 토큰을 채팅에 붙여넣도록 요구하지 않고 실행 환경의 비밀값 설정을 사용한다.

단계별로 API 접근 가능성을 먼저 확인한다. 인증·권한이 막히면 원인과 막힌 단계를 남기고, 작동을 확인하지 않은 수집기를 배포하지 않는다. 이번 요청의 산출물은 계획서이며 구현 시작·외부 비용 집행을 뜻하지 않는다.

## 10. 검증 항목

- 실제 글 3~5개를 골라 본문·게시 시각·원문 링크와 화면에 보이는 조회/반응을 대조한다. 관측 시각 차이·반영 지연은 구분해 기록한다.
- 2페이지 이상 목록 조회, 일부 본문 없음, 긴 본문, 인용/리포스트를 검증한다.
- 미제공 값·0·지표 조회 실패가 구별되는지 검증한다.
- 중복 실행, 쓰기 타임아웃 후 재시도, 부분 실패 후 재실행에서 행 중복이 생기지 않는지 검증한다.
- 실패한 수집으로 정상 데이터·관측 시각·직접 메모가 바뀌지 않는지 검증한다.
- 인증 만료·권한 오류·호출 제한을 재현하고 마지막 성공 데이터와 오류 상태가 남는지 검증한다.
- 두 줄 요약에 표본·확인 범위가 포함되고, 서로 다른 시점의 값이나 화면/PDF 지표를 API 값과 혼합하지 않는지 확인한다.

## 11. 2차 확장 기준

실제 사용 중 아래 질문이 반복될 때만 확장한다.

| 필요 | 추가 개발 |
|---|---|
| 글이 시간이 지나며 얼마나 늘었는지 알고 싶다 | 별도 성과 관측 DB에 게시글 ID·관측 시각·지표를 보존. 현재값 덮어쓰기만으로 과거 증가량을 계산하지 않음 |
| 게시 후 24/48시간을 비교하고 싶다 | 시작 이후 관측값과 실제 경과 시간을 저장. 하루 2회 수집은 정확히 24/48시간 관측을 보장하지 않으므로 허용 오차를 정하거나 수집 주기를 조정 |
| 어떤 대화가 생기는지 알고 싶다 | 댓글 읽기 권한·중첩 구조를 검증하고 본인 답글/외부 답글·응답자·재참여를 구분. 원문 링크와 근거 범위를 함께 보존 |
| 같은 맥락으로 글감 추천을 받고 싶다 | 기존 예약에서 최신 DB와 사용자 메모를 읽도록 연결. 경험·의견·게시 결정과 대화는 사용자 중심으로 유지 |

사람이 중심인 운영 원칙은 고정한다. AI만으로 운영되는 계정의 장기 성과에 대한 사용자의 판단은 운영 가설로 존중하며, 데이터가 이를 입증한 것으로 표현하지 않는다.
